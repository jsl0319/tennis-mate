## 2. 검증 기준

Rally On의 첫 유료 모델에는 아래 조건이 모두 필요하다.

1. 모집자 한 명만 코트 이용 총액을 실제 결제한다.
2. 참가자는 앱 결제·환불·비용 수납 대상이 아니다.
3. 모집자 결제 승인, 전액 취소, 환불, 운영자 지급을 각각 추적하고 중복 처리하지 않는다.
4. 운영자의 사업자·정산 온보딩은 PG가 처리하며, Rally On은 계좌·카드 원문을 저장하지 않는다.
5. 운영자 공급 철회·시설 폐쇄·안전 위험·사용 불가 우천·재난에는 모집자 전액 환불을 만들 수 있어야 한다.
6. 코트 이용 총액·수수료·환불·지급 내역을 원장과 PG 데이터로 대사할 수 있어야 한다.
7. 기존 Pilot의 `AVAILABLE → ALLOCATED` 단일 Slot 배정과 서버 권한 모델을 훼손하지 않는다.

## 3. 공식 문서 기반 후보 비교

| 후보 | 확인된 적합 기능 | 결론 |
| --- | --- | --- |
| **토스페이먼츠** | 결제 승인·조회·전액/부분 취소·멱등 취소, 정산 조회, 오픈마켓 셀러 등록·지급대행·셀러/지급 상태 웹훅 | **1순위 조건부 권장**. 필요한 결제와 지급대행 기능이 공개 문서에서 모두 확인됨. 계약과 지급 시점 게이트가 통과해야 함. |
| PortOne | 하위상점별 PG 채널, 결제 조회·취소, 하위상점별 웹훅 | **예비 후보**. 공개 문서로는 결제 채널 분리와 취소·웹훅은 확인되지만, Rally On이 요구하는 운영자별 지급대행·보류·대사 계약은 확인하지 못함. 신규 구현의 기반으로 선택하지 않음. |
| 네이버페이 | 결제형 개발환경과 정산 API, 2차 PG를 위한 차액 정산 API | **추후 결제수단 후보**. 단일 결제와 운영자 지급의 기반 PG로는 적합성을 확인하지 못함. 차액 정산 설명은 금융감독원 등록 2차 PG의 하부 가맹점 전제가 있어 Rally On에 바로 적용할 수 없음. |

토스페이먼츠 공식 문서는 지급대행을 “오픈마켓을 대신하여 셀러에게 지급”하는 서비스로 정의한다. 셀러 등록, 지급 가능 잔액 조회, 지급 요청, 셀러·지급 상태 웹훅을 제공하므로 Court Commerce의 단일 모집자 결제와 운영자 지급 구조에 가장 가깝다. 다만 이 사실만으로 Rally On의 업종·계약상 판매자·환불/세무 책임이 확정되지는 않는다.

## 4. 1순위 후보 적합성 — 토스페이먼츠

### 4.1 결제와 환불

- `paymentKey`와 `orderId`는 결제 승인·조회·취소에 쓰이는 지속 식별자이므로, `CommercePayment.providerPaymentRef`와 `providerOrderRef`의 유일 제약에 맞는다.
- 결제 취소 API는 전액·부분 취소를 지원하며, 멱등 키로 중복 취소를 방지할 수 있다. 첫 출시 정책은 전액 환불만 만들고 부분 환불은 비범위로 유지한다.
- 카드 결제는 매입 후 취소에 영업일 기준 3~4일이 걸릴 수 있다. 따라서 앱은 `환불 요청됨`과 `환불 완료`를 같은 상태로 표시하면 안 된다.
- 가상계좌 취소에는 환불 계좌 정보가 필요할 수 있고, 입금 대기 상태는 15분 Slot 홀드와 맞지 않는다. **첫 출시 결제수단은 카드와 간편결제로 제한**하고, 가상계좌·휴대폰·에스크로는 별도 계약·환불·상태 설계가 승인되기 전 제공하지 않는 것을 권장한다.

### 4.2 운영자 지급과 KYC

- 지급대행은 셀러 등록과 지급 가능 잔액 확인 뒤에 요청한다. 지급 POST는 JWE 암호화가 요구되며, 정산 잔액 조회와 지급 상태 웹훅이 제공된다.
- 개인·개인사업자 셀러는 본인인증 후 주당 1천만원 미만 지급만 가능한 `PARTIALLY_APPROVED` 상태가 될 수 있다. 주당 1천만원 이상 지급 시 KYC가 필요하며, 심사가 끝나기 전에는 지급할 수 없다.
- 테스트 환경은 유효한 사업자번호의 법인 셀러만 등록 가능하고 KYC 완료 상태를 재현할 수 없다. 따라서 sandbox는 결제·취소·웹훅·법인 셀러 지급 흐름까지만 자동 검증하고, 실제 운영자 유형의 지급 적합성은 계약 뒤 제한된 실거래 Pilot으로 별도 확인해야 한다.

`OperatorCommerceAccount.status`는 단순 `ACTIVE` 하나로 PG 상태를 덮어쓰면 안 된다. 실제 구현 때에는 제공자 원문 상태를 안전하게 매핑해 최소 `ONBOARDING`, `PAYOUT_LIMITED`, `KYC_REQUIRED`, `ACTIVE`, `SUSPENDED`와 마지막 동기화 시각을 보관한다. 사용자에게는 “정산 준비 중”, “추가 확인 필요” 같은 안전한 상태만 보이며 KYC 원문과 민감 정보를 반환하지 않는다.

### 4.3 지급 시점 — 사전 검증에서 확인된 필수 게이트

토스페이먼츠는 지급한 금액의 회수가 어렵다고 명시한다. 그러므로 운영자에게 모집자 결제 **승인 사실**을 즉시 보여 주는 것과 운영자에게 실제로 **지급 요청**하는 시점을 분리해야 한다.

권장안은 다음과 같다.

1. 모집자 결제 승인 뒤 유료 Match와 Slot을 확정하고, 운영자 화면에는 `모집자 결제 완료`를 표시한다.
2. 지급 요청은 `endsAt` 이후이면서 공급 철회 Incident·환불 요청·미결제/미확정 상태가 없고, PG `availableAmount`가 충분할 때만 만든다.
3. PG의 실제 정산 주기와 법무·세무 검토에 따라 운영 보류 기간·마이너스 정산/환수 책임을 확정한다. `EXPRESS` 지급이나 수동 조기 지급은 첫 출시에서 제공하지 않는다.
4. 지급 요청·성공·실패·재시도는 각각 불변 원장 행과 PG 지급 참조를 남기며, 실패한 멱등 요청은 임의로 새 키로 재전송하지 않는다.

이 게이트는 24시간 전 모집자 취소와 공급 철회 전액 환불 정책을 바꾸지 않는다. “실제 결제가 확인됐다”는 운영자의 불안을 줄이면서, 환불 대상 금액을 먼저 되돌리기 어려운 지급으로 보내지 않기 위한 보호다.

### 4.4 웹훅·대사·sandbox

- 결제 상태, 취소 상태, 셀러 상태, 지급 상태 웹훅을 모두 받아야 한다. 클라이언트 성공 리다이렉트만으로 `PAID`나 `ALLOCATED`를 확정하지 않는다.
- 정산 조회 기록은 테스트 환경에서 비어 있을 수 있으므로, 정산 대사 전체를 sandbox 통과 조건으로 오해하면 안 된다. live 계약 뒤에는 소액의 통제된 Pilot 결제로 지급·취소·대사를 별도 검증한다.
- 테스트 환경에서는 에러 코드 재현이 가능하므로, 승인 실패·지연·취소 실패·웹훅 재전송을 자동 테스트에 포함한다.
- 지급대행은 POST 본문 JWE 암호화를 요구한다. 키는 서버 환경 변수/비밀 저장소에만 두고, 로그·DB·브라우저·Git에 저장하지 않는다.

## 5. 계약·법무·세무 확인 없이는 통과할 수 없는 항목

아래는 공개 API 문서로 판단할 수 없는 **차단 항목**이다. 토스페이먼츠 담당자와 법무·세무 담당자의 서면 답변이 있어야 구현 게이트를 닫는다.

| 질문 | 확인해야 할 답 |
| --- | --- |
| 계약 구조 | Rally On이 플랫폼으로 모집자의 코트 이용 총액을 받고, 개별 코트 운영자에게 지급대행하는 구조가 허용되는지. 계약상 판매자·환불 주체·정산 주체는 누구인지 |
| 업종·제공 방식 | 시간 단위 테니스 코트 이용권/현장 서비스가 허용 업종인지, 운영자의 개인사업자·법인 유형별 가입/심사 요건은 무엇인지 |
| 수수료와 세금 | PG 수수료·지급대행 수수료·취소/환불 수수료·부가세·세금계산서/영수증 발급 책임 및 정산 주기 |
| 환불과 지급 보류 | 시작 24시간 전 전액 취소, 공급 철회 전액 환불, 지급 후 환불/차지백의 상계·환수·보류금 규칙 |
| KYC와 한도 | 개인사업자·법인 각각의 본인인증, 주간 한도, KYC 재심사, 상태 변경 알림, KYC 미통과 시 운영자/세션 처리 |
| 데이터 처리 | PG가 수집하는 정산계좌·연락처의 위수탁/제3자 제공 고지, 보관 기간, 고객 문의·민원 처리 창구 |
| sandbox와 실거래 Pilot | 셀러/지급대행 테스트 범위, 테스트 한계, 소액 live Pilot의 비용·취소·환불·대사 검증 절차 |

현재 `/terms`와 `/privacy`는 결제 없는 비공개 MVP 안내다. 계약이 확정되기 전에는 수정하지 않는다. 유료 출시 전에는 판매자/플랫폼 역할, 총액·24시간 취소·예외 환불, 환불 상태·문의 채널, PG 개인정보 처리와 지급/정산의 책임을 법무 검토한 문구로 새로 공개해야 한다.

## 6. 권장 RFI(계약 문의) 초안

> 테니스 코트 운영자와 이용자를 연결하는 온라인 서비스를 준비하고 있습니다. 운영자가 시간·총 이용료·최대 인원을 등록하면 일반 모집자 한 명이 코트 이용 총액을 카드/간편결제로 결제하고, 운영자는 서비스 이용 종료 뒤 지급을 받는 구조입니다. 참가자는 서비스 내 결제 대상이 아니며 현장에서 자율 정산합니다. 개별 운영자는 사업자등록증을 보유한 개인사업자 또는 법인입니다. 토스페이먼츠 결제 + 지급대행 계약으로 이 구조가 가능한지, 판매자/환불/세무 책임, 허용 업종, 셀러 KYC·주간 한도, 지급 보류·환수, 수수료·정산 주기, sandbox와 소액 live Pilot 절차를 서면으로 안내해 주세요.

이 문의에는 실제 사업자등록번호, 정산 계좌, 사용자 개인정보, API 키를 첨부하지 않는다.

## 7. 사전 검증 결과와 다음 게이트

### 7.1 결과

| 기준 | 결과 | 근거/후속 조치 |
| --- | --- | --- |
| 단일 모집자 결제 | 조건부 통과 | 토스페이먼츠 결제 승인·조회·취소 API 확인. 카드·간편결제로 범위 제한 권장 |
| 24시간 전 전액 취소 | 조건부 통과 | 전액 취소·멱등 지원 확인. 실제 취소 가능 기한·처리 기간은 결제수단별 계약을 확인 |
| 운영자별 지급 | 조건부 통과 | 셀러 등록·KYC·지급대행·상태 웹훅 확인. 계약상 판매자·업종·한도 확인 필요 |

| 정산 대사 | 조건부 통과 | 결제·정산·지급 식별자와 상태 조회 수단은 확인. sandbox 정산 기록 한계가 있어 live Pilot 필요 |
| 법무·세무·약관 | 보류 | 현재 약관/개인정보 처리방침은 비결제 MVP용. 계약 확정 뒤 별도 검토·공개 필요 |

### 7.2 구현 시작 전 순서

1. 사용자가 위 RFI를 토스페이먼츠에 보내고, 서면 답변·견적·계약서를 확보한다.
2. 법무·세무 검토로 판매자·환불·지급·보류·영수증/세금계산서·개인정보 고지를 확정한다.
3. 카드·간편결제만 사용하는 테스트 상점과 법인 셀러 fixture로 sandbox 결제·취소·웹훅·지급대행을 검증한다.
4. 결제·지급 담당자, PG 장애와 환불 실패의 운영 절차, 지원 채널을 정한다.
5. 위 결과가 문서화되면 그때에만 Commerce migration·서버 API·모바일 UI를 별도 요청으로 구현한다.
